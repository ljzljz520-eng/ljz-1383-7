# 播客主持人主页系统

零依赖（Python 3 标准库 + SQLite/FTS5）的播客站点与管理系统。

## 运行

```bash
python3 seed.py          # 初始化演示数据（可选，首次启动会自动建库）
python3 run.py 8000      # 启动服务
# 公开站点  http://127.0.0.1:8000/
# 管理后台  http://127.0.0.1:8000/admin?key=admin-dev-key   (密钥见环境变量 ADMIN_KEY)
python3 acceptance_tests.py   # 28 项验收测试（独立端口与临时库）
```

## 结构

| 模块 | 职责 |
|---|---|
| `podcast/db.py` | 模式定义：单集/话题/嘉宾/音轨修订/编辑映射/注释/授权/渠道版本/计划/流水线事件/RSS缓存/播放器回调/商务表单/FTS |
| `podcast/edits.py` | 编辑映射核心：delete/insert 操作编译为原子区间，注释区间重定位 |
| `podcast/core.py` | 领域逻辑：修订登记、重定位、分阶段流水线、发布闸门、调度器、RSS 水位线缓存、搜索、播放器回调 |
| `podcast/web.py` | HTTP 层：公开页（话题/单集/搜索/商务表单/RSS/播放器API）+ 管理后台 |

## 核心机制

### 1. 重新剪辑后的时间码重定位（编辑映射）
每次重新剪辑/换音轨产生新 `audio_revisions` 行，并携带 ops：
`{"op":"delete","start":S,"end":E}` / `{"op":"insert","at":P,"length":L}`（毫秒，半开区间）。

- 字幕、章节、嘉宾授权片段按修订版本 copy-on-write 复制，经映射函数平移到新秒数，**绝不原封保留旧秒数**；
- 落入删除区（`source_deleted`）、横跨删除点（`partial_overlap`）、映射后零长度的注释进入 **待修复**（`pending_repair`），保留旧时间码供人工核对，后台可“修复（给定新时间码）/丢弃”；
- 待修复注释不进播放器 API、不进全文索引、不进 RSS。

### 2. 分阶段流水线与缺音频策略
发布/换版本时按序执行并落库 `publish_events`：
**transcode**（模拟转码→ready/missing）→ **index**（重建该集 FTS）→ **rss**（递增渠道代次使缓存失效）。

发布闸门检查：嘉宾授权齐全 → 音频就绪？缺音频时按单集策略分流：
`transcript_public` → 以**文字稿回退**公开上线（渠道版本 `transcript_only=1`，页面展示文字稿，RSS 无 enclosure）；
`hold` → **暂缓发布**（状态 held，不进 RSS/搜索）。

### 3. 定时上线与授权闸门
`publish_schedules` 到期由调度器处理；上线前重新校验嘉宾授权，
**授权被撤销则计划 blocked、单集不上线**并记录原因。已上线期间授权被撤销 → 立即下架（held）并使 RSS/索引失效。

### 4. RSS 缓存（水位线自愈）
缓存行携带水位线 = 已发布集数 : 最大 updated_at : 修订ID和 : 渠道代次。
任何发布面变化（包括“忘记走失效流程”的直接改库）都会使水位线失配 → 自动重建，避免“RSS缓存未刷新”。

### 5. 播放器旧回调
回调携带 `revision_id`，与当前渠道版本比对：旧修订回调**记录但不应用**（`applied=0, note=stale_revision`），统计与播放位置不被过期事件污染。

### 6. 权限分离
- 商务表单写入 `inquiries`，仅管理密钥可读（`/api/inquiries` 公开访问 403）；
- 全文索引只含“已发布单集当前渠道版本的 active 注释”，查询时再按当前发布状态二次过滤——**未公开访谈片段不可能被搜到**；
- 单集页呈现**实际渠道版本**（`channel=public|member`，可播不同剪辑），缺音频时明确标注文字稿回退。

## 固定媒体版本 vs 永久单集地址（允许更新音频）

| 维度 | 固定媒体版本发布（每期一个不可变媒体文件，更新即发新 URL/新单集） | 永久单集地址（guid/链接不变，音频可换修订） |
|---|---|---|
| **缓存** | CDN/边缘缓存可永久强缓存（immutable），无失效问题；但修正错误只能发新版，旧文件永远残留 | 需要失效机制：本系统用渠道代次+水位线使 RSS/缓存自愈；媒体文件本身建议按修订版本命名（v1.mp3→v2.mp3）规避 CDN 旧文件 |
| **订阅客户端** | 客户端把新版当新单集，听众重复收到、已听状态丢失；旧版仍被已下载者保留 | 客户端按 guid 去重，重抓 RSS 后静默换新 enclosure；但**已下载旧音频的客户端不会自动更新**，播放统计跨修订需按 revision_id 区分（本系统播放器回调即如此） |
| **历史引用** | 时间码引用（“32:10 那句话”）永久有效，因为媒体不变；外链永不失效 | 旧时间码失效——必须靠**编辑映射**把字幕/章节/授权片段重定位，无法映射的进待修复；本系统保留全部旧修订与 edit_maps，历史引用可回溯到具体 revision |
| **适用** | 定稿不再改的节目、合规要求留档 | 需要修错、换广告、重剪辑的在播节目 |

本系统采用**永久单集地址 + 修订化媒体**：对外 slug/guid 不变，内部 `audio_revisions` 逐版递增，
兼顾可更新性与历史可回溯性。

## 验收场景覆盖（acceptance_tests.py，28 项）
1. 删掉一段嘉宾发言 → 注释平移/待修复（含授权片段保留旧时间码供人工处置）
2. 换音轨 → 渠道版本切换、播放器拿到新媒体、字幕为重定位后秒数
3. 定时上线时授权被撤销 → 计划 blocked、单集不上线、RSS 不含、原因落库
4. RSS 缓存未刷新 → 水位线识别过期缓存并重建
5. 播放器旧回调到达 → 记录不应用，统计只计有效回调
6. 缺音频策略 → 公开文字稿 vs 暂缓发布
7. 权限分离 → 未公开访谈搜不到、商务表单仅管理员可读
